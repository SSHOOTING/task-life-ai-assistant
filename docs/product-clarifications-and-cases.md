# 首版产品确认与验收用例

本稿供团队评审。基于 [PRD v0.7](PRD_v0.7.docx)、[MVP 技术 SPEC](MVP_SPEC_v1.0.docx) 和[组长确认清单](open-questions.md)，落实日记、打卡和回顾的产品口径，并补上对应的白盒检查。评审后的结论同步回 SPEC、共享接口和[验收基线](acceptance-cases.md)。

## 产品确认

| 清单编号 | 确认内容 |
| --- | --- |
| Q-01 | 一次输入可识别任务、进展、当天打卡、日记等多种内容。固定主用例新增一条完整原话、两条事项记录和一条日记片段。三条派生记录都指向同一次输入。 |
| Q-02 | 当天打卡复用 `daily_task`。用户自行设置最多三项进行中的长期习惯。清楚的单次完成直接记在当天，无须查询历史来猜用户是否要设长期习惯。可以在设置入口或合适的对话中邀请用户自行选择。只有明确指定习惯或从该习惯入口打卡，才把当日记录计入该习惯。 |
| Q-03 | 提议在 `raw_events` 和 `tasks` 之外新增一张 `reflections` 表。保存用户、日记原话、来源输入、发生日期、来源类型和可留空的相关任务。来源类型区分随手记和晚间回顾中的主动分享，以对话场合为准。晚间回顾可引用白天已有记录，用户可以分享、跳过或结束。 |
| Q-04 | F6 晚间收尾和 F7 提醒的最小版优先，作为试用前的最低要求。F6 在确认明日安排后提供文字摘要和 H5 全天简表。F8 周回顾其次，争取在试用前交付，日记从开始即按可供周回顾读取的方式留存。F9 画像后置。 |
| Q-05 | 生活感受生成独立日记记录，可关联明确的已有任务。关联本身不创建或改变任务。随手记和晚间日记都可用于回顾。试用版通过回顾呈现，逐条查看、排除和撤销按钮可后置。保留用户原话，不自动贴情绪标签。 |

沿用原话留存、来源可追溯、纠正留历史、失败无半成品四项原则。整次解析失败时保留原话，任务和日记均零写入。解析正常但个别事项存疑时，明确项照常保存，存疑项合并澄清，回执说清每部分的结果。原话留存适用于正常录入和纠正，用户明确要求删除时按 Q-13 执行。

Q-06 至 Q-16 全部采用 `docs/open-questions.md` 的默认口径。其中“别当任务”允许保留日记，“这句别记”按明确不留存或删除处理。涉及混合输入中的局部删除或备份清理时限，由团队按 Q-13 细化实现和测试。

## 主用例与补充用例

下表的“白盒检查”列出解析、归属或写入后的可核对结果。增量均相对于测试开始前的数据。原有 TC-002 至 TC-014 保留验收目的，涉及日记写入、查询、权限和回溯的断言按新基线同步。五个补充场景待评审后分配正式编号。

| 用例 | 前置与用户输入 | 白盒检查 | 用户所见与红线 |
| --- | --- | --- | --- |
| TC-001 主用例更新 | 已有进行中的「毕业论文」。用户说“今天背完单词了，论文开头也改了，跟朋友聊完没那么焦虑了。” | 解析出当天打卡、论文局部进展、随手记。`raw_events` +1，`tasks` +2，`reflections` +1。三条派生记录同源。论文进展指向「毕业论文」，感受的任务关联留空。 | 一条回执说明记下了三项。论文保持进行中。朋友聊天不变成任务，感受不被挂到论文。 |
| 补充 1 晚间分享与跳过 | 主动进入晚间回顾。分别输入“我发现今天就算没做完，也没那么急着赶了”和“今天就到这里吧”。两条分开测。 | 分享时新增一条晚间日记，保留完整原话，任务关联为空。结束指令使本轮回顾结束，新增日记为零。 | 分享可以被回应。用户结束时停止追问，不生成空日记，也不自动安排明天。 |
| 补充 2 晚间引用白天原话 | 白天已留下“开完会好累”。晚间助手提起这句，用户补充“其实我最累的是怕漏掉别人的事”。 | 助手引用时读取已有片段，日记数不变。用户补充后新增一条晚间日记，链接到本轮用户原话。后续周回顾可读取两段用户原话。 | 用户能看出哪句是白天说的、哪句是晚上的新想法。助手回述不计为用户的新日记。 |
| 补充 3 单次打卡与长期习惯 | 测试账号未设置长期「背单词」习惯。用户说“今天背完单词了”。 | 当天新增一条 `daily_task`，状态为完成，长期习惯关联为空。长期习惯数量及提醒计划维持原样。 | 回执只确认当天完成。设置长期习惯可以随后由用户自主选择。 |
| 补充 4 会议分工、交接与返工 | 已有进行中的「学术会议筹备」。①“我周四中午发最终名单，小李周三交初版，小周等人数定了订盒饭。名单一直没定，我有点着急。” ②“初版改由小王接手，小李把已有版本交给他。” ③“收到小王的初版，还少两位，让他明早十点前补齐。” | ① 同一会议下识别本人交付、他人负责的步骤及依赖。感受留为一条随手记，可关联会议。② 更换同一初版步骤的负责人，保留交接。③ 更新同一步骤的返工要求与时间，保留已收到初版的进展，整个会议仍进行中。 | 用户看得出谁做什么、下一步卡在哪里。初版影响用户发最终名单时，可合并问一次是否跟进。未获确认不自动设提醒。小李、小周、小王的工作不计为用户本人的待办，不替用户向他人发消息。 |
| 补充 5 日常生活与愿望 | 用户说“今天跟朋友去爬山，聊得特别开心。山上都是红红的叶子，南京的秋天真好看，下次还想去。” 用户没有要求记待办、提醒或打卡。 | `raw_events` +1，`reflections` +1。连起来保留爬山、聊天、秋景和愿望的原话，日记无任务关联。`tasks`、打卡和提醒均无新增，可供周回顾选用。 | 简短回应即可。不得从“下次还想去”生成爬山待办或追问时间，也不把这次爬山自动记成健身打卡。 |

## 评审后的同步

- 将 Q-01 至 Q-05 的结论和 Q-06 至 Q-16 采用默认的确认写回 `open-questions.md`。技术 SPEC 同步更新首版范围、数据模型、回执契约和验收章节。
- `acceptance-cases.md` 更新 TC-001 的写入预期，并把补充场景并入现有编号。已有的去重和失败用例加查 `reflections`，核对重试不产生重复片段、失败不留下半成品。
- 补充 4 对应 PRD v0.7 的会议人工冒烟。会议步骤的具体存储和变更历史由团队评审，保持使用通用任务能力。F7 开发时另验一次真正的提醒到时与失败状态，依据 Q-07 的确认口径。
