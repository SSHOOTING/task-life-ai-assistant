# 验收用例与数据状态基线

> 当前基线：原始记录表 `raw_events` + 任务表 `tasks`。
>
> 目标：每个 Case 不仅验证回执文字，还要验证原始 Log、任务数据库和关联关系。
>
> 当前实现：TC-001 已独立验收通过；TC-002 至 TC-014 仍明确跳过，不能算通过。

## 1. 怎么看这份文档

| 名词 | 人话解释 |
|---|---|
| 原始 Log | `raw_events`，保存用户每次发言和平台收到的时间、来源、解析状态、首次回执 |
| 任务数据库 | `tasks`，保存当前任务、进展和打卡状态 |
| 操作前 | 执行本 Case 之前，两张表应处于的状态 |
| 操作后 | 执行成功后，两张表应处于的状态 |
| 零写入 | 请求失败或只读查询时，两张表的行数和关键字段都不变化 |
| skip | 只登记了验收意图，没有执行完整断言；不能算通过 |

数据库计数统一写成“原始 Log 条数 / 任务条数”，例如 `1 / 2` 表示一条原始记录和两条任务。

## 4. 跨 Case 不变量

| 不变量 | 验收含义 |
|---|---|
| 原话保留 | 任何成功、失败、纠正或重复请求都不得改写原始 Log 的 `content` |
| 来源可追溯 | 每条任务必须能回到唯一的原始 Log |
| 纠正可回放 | 纠正是新记录，任务是当前状态，历史不覆盖 |
| 用户隔离 | 任何查询和纠正都必须带用户边界 |
| 失败零写入 | 解析失败只保留原话；鉴权和校验失败不写任何业务数据 |
| 生活感受不任务化 | 感受只保留原话，不生成情绪标签或 `reflection` 任务行 |
